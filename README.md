## 两篇报告的关系

第一篇回答 **"能跑多大的模型"**；第二篇回答 **"还能压榨出多少"**，并给出了一个否定但有用的答案——沿途发现了三样第一篇里没有的东西：**一个 6 倍速的工具调用模型、一个可用的决策模型、以及这条硬件路线的精确天花板及其根因**。

第二篇对第一篇的**修正**：

| 第一篇结论 | 第二篇修正 |
|:---|:---|
| 350M 是"甜点位，可用" | 速度可用，但**受约束分类只有 1/5（20%）**——它是生成模型，不是控制模型 |
| "2–3 线程就带宽饱和" | 错。1/2/4 线程 = 3.11 / 5.59 / **10.32** t/s，近线性 |
| 瓶颈可能在带宽 | 错。**算力受限**：Q8_0 体积大 72%，速度只掉 5% |
| — | **新增**：速度由内核家族决定（Q6_K 比 Q8_0 慢 32%） |
| — | **新增**：prefix cache 带来 15× 端到端加速 |
| — | **新增**：d1-omni-600M 分类 83%，Needle 2 工具调用 63 t/s |

## 核心结论速览（第二篇）

### 十条关键判断

| # | 结论 | 关键证据 |
|---|---|---|
| 1 | **瓶颈是算力，不是带宽** | Q8_0 大 72%，速度只掉 5% |
| 2 | **速度由内核家族决定，不是位宽** | Q6_K(280MB) 比 Q8_0(362MB) 慢 32% |
| 3 | **没有任何引擎能超过 llama.cpp** | 国产 6 + 国外 4 全部证否 |
| 4 | **根因在 A53 微架构** | 2×64-bit NEON → 4 MAC/cycle → int8 不比 FP32 快 |
| 5 | **自研引擎上限 1.3–1.5×，需 3–6 人月** | Arm 官方：dotprod 差 5.5×，是 ISA 级差距 |
| 6 | **最大单项收益是 prefix cache（15×）** | 多轮对话第 2 轮起 12.2 s → 0.8 s |
| 7 | **prompt 长度是成本主变量** | 每 100 token = 5.4 秒 |
| 8 | **d1-omni-600M 可跑，分类 83%** | 350M 聊天模型只有 20% |
| 9 | **Needle 2 快 6 倍但不懂中文** | 63.3 t/s / 42 MB / 0.58 s，中文直接崩溃 |
| 10 | **1512 MHz 是这颗芯片的物理终点** | OPP 存在但被 bin 门控；vdd 上限 1.1 V |
